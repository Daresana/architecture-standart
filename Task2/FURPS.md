| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | **Функциональные требования** | |
| F1 | На сайте клиент видит доступные депозиты и действующие общие ставки. | |
| F2 | Клиент оставляет на сайте заявку с Ф. И. О. и телефоном. Заявка поступает в кол-центр. | |
| F3 | Оператор звонит клиенту и обсуждает условия. Новый клиент проходит проверку документов в отделении. | Особые условия согласуются с бэк-офисом. |
| F4 | В интернет-банке клиент видит депозиты, накопительные счета, общие и свои персональные ставки. | |
| F5 | Клиент выбирает свой счёт и сумму, проверяет условия и подтверждает заявку СМС-кодом. | |
| F6 | Кредитный и депозитный бэк-офисы ведут и согласуют ставки в АБС. | Сейчас ставки хранятся в Excel. Утверждённые ставки нужно хранить в одном месте. |
| F7 | В MVP сотрудник депозитного бэк-офиса обрабатывает заявку и подтверждает условия в АБС. | Автоматическое открытие запланировано на год. |
| F8 | Клиент получает СМС о согласовании ставки и об открытии депозита. Статус заявки виден в интернет-банке. | Добавлено: клиент должен видеть результат обработки заявки. |
| F9 | Если условия изменились, клиент подтверждает их заново до открытия депозита. | Добавлено: согласование сотрудником не заменяет согласие клиента. |
| U | **Удобство использования** | |
| U1 | Новые страницы используют дизайн-систему банка. | |
| U2 | Форма понятно показывает условия, счёт, сумму, ошибки и результат отправки. | Добавлено с учётом клиентов старшего возраста. |
| R | **Надёжность** | |
| R1 | Онлайн-сервисы работают круглосуточно. Целевая доступность — не ниже 99,9%. | Текущая инфраструктура не обеспечивает этот показатель. Его нужно проверить после доработок. |
| R2 | При отказе основного ЦОД работа восстанавливается в резервном. Принятые заявки сохраняются. | При доступности 99,9% допустимый простой составляет около 43 минут за 30 дней. Время восстановления, допустимую потерю данных и правила расчёта доступности нужно согласовать. |
| R3 | При отказе АБС можно подать заявку и посмотреть действующие ставки. Обработка продолжится после восстановления АБС. | Открытие счёта во время отказа АБС не обещается. |
| R4 | Повторная отправка заявки или сообщения не создаёт второй депозит. | Добавлено: при сбоях сообщения могут приходить повторно. Для проверки используются идентификаторы заявок и сообщений. |
| R5 | У ставки есть версия и срок действия. Просроченная ставка не показывается как актуальная. | Добавлено: обновления приходят в системы с задержкой. |
| P | **Производительность** | |
| P1 | Просмотр ставок и приём заявки должны отвечать быстро. | Предварительно: не менее 95% запросов к API выполняются за 500 мс или быстрее. Это показатель p95. Ожидание СМС и работы сотрудника сюда не входит. В задании точного времени нет; значение и нагрузку нужно согласовать. |
| P2 | Новый процесс получает справочные данные без постоянных запросов к базе АБС. | Доработка существующих платежей не входит в MVP депозитов. Их проблемы со скоростью нужно изучить отдельно. |
| P3 | Веб-часть и новые сервисы можно запускать в нескольких экземплярах и распределять между ними запросы. | Для MS SQL нужны копирование данных и управляемое переключение основного узла. |
| P4 | Обмен с АБС идёт порциями и с ограничением скорости. | Это снижает нагрузку на Oracle. Увеличивать её мощность можно за счёт ресурсов сервера. |
| S | **Сопровождение** | |
| S1 | Описаны форматы API и сообщений, статусы заявок и порядок обновления ставок. | Это нужно для поддержки и подключения новых продуктов. |
| S2 | Проверяются обмен данными, повторные сообщения, отказ АБС и переключение ЦОД. | Добавлено для проверки надёжности решения. |
| S3 | Поддержка видит ошибки обмена, задержавшиеся заявки и время последнего обновления ставок. | Добавлено: ошибка может возникнуть уже после приёма заявки. |
| +R | **Ограничения** | |
| +R1 | Учитываются существующие технологии: ASP.NET MVC/.NET Framework и MS SQL, Delphi/PL-SQL и Oracle, PHP/React, Java Spring Boot/React/PostgreSQL. | Для новых компонентов выбираются совместимые технологии, знакомые команде банка. |
| +R2 | Команда банка разрабатывает новый процесс депозитов и отправку СМС без доработки ядра подрядчиком. | Изменения существующего механизма СМС зависят от подрядчика. |
| +R3 | Новый процесс не обращается напрямую из интернет-банка к базе или API АБС. | Существующая связь для платежей и текущих счетов остаётся за пределами изменений. |
| +R4 | Если нужна очередь сообщений, используется Kafka. | Старый интернет-банк с ней несовместим. К Kafka подключается новый сервис. |
| +R5 | Данные сайта и интернет-банка передаются по защищённым соединениям. Доступ к персональным данным ограничен. | Для API используется HTTPS/TLS. Соединения с брокером и базами также защищаются, участники проходят проверку доступа. |
| +R6 | Кредитный и депозитный отделы имеют доступ только к разрешённым данным. Клиент видит только свои заявки и персональные предложения. | Совместная работа со ставками не открывает доступ к закрытым данным другого отдела. |
| +R7 | СМС-код связан с клиентом, заявкой и условиями. Он действует ограниченное время и используется один раз. | Добавлено: срок действия и число попыток нужно согласовать со специалистами по безопасности. |
| +R8 | MVP выпускается через шесть месяцев. Через год депозиты и накопительные счета открываются автоматически; в отделении участвует только фронт-офис. | Онлайн-оформление кредитов в этот MVP не входит. |
