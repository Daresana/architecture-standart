### **Решение**

Схемы: [контекст](C4-context.drawio) и [компоненты](C4-components.drawio). Рядом находятся SVG для просмотра.

Здесь показана передача общих ставок. Приём и обработка заявок описаны в [ST-ADR-1](../Task3/ADR.md).

Используем утверждённые ставки из АБС и их копию в сервисе депозитов. Сотрудники продолжают расчёт в Excel, затем загружают и согласуют ставки в АБС. Новые каналы получают опубликованную версию из системы.

**Компоненты сервиса**

| Компонент | Назначение |
| :- | :- |
| Получатель ставок | Получает сообщения из Kafka, проверяет версию и сохраняет данные. Отделяет персональные предложения от общих. |
| Хранилище ставок | Читает и записывает ставки в MS SQL. Возвращает общие условия и срок действия. |
| API общих ставок | Передаёт кол-центру банка разрешённые поля по HTTPS. |
| Выгрузка ставок | Создаёт CSV, загружает его на SFTP и повторяет отправку при ошибке. |

Все четыре компонента входят в один сервис депозитов.

**Кол-центр банка**

Подрядчик дорабатывает систему кол-центра. Сервер Java Spring Boot получает ставки, интерфейс React показывает условия и время обновления.

Если API недоступен, система показывает последнюю действующую копию и предупреждение. После окончания срока действия оператор не сообщает числовую ставку до обновления данных.

**Передача партнёру**

IT разворачивает SFTP-сервер с резервированием в отдельной зоне обмена. Каталог партнёра отделён от внутренних систем банка. Сервис загружает файл, партнёр забирает его своей учётной записью.

CSV содержит версию, код и название продукта, валюту, срок, диапазон суммы, ставку, начало и конец её действия. Разные сочетания условий записываются отдельными строками.

Кодировка файла — UTF-8. Разделитель и запись чисел согласуются с партнёром.

Сначала файл загружается под временным именем. После завершения он получает имя `rates_<version>.csv`. Партнёр читает только готовые файлы.

Новая версия выгружается после публикации. Неудачная отправка повторяется по расписанию. При повторе сохраняются имя и содержимое файла. Более старая версия не должна заменять новую.

Успешная загрузка на SFTP подтверждает передачу файла на сервер. Загрузку данных в систему партнёра проверяют отдельно при подключении. Дальнейший контроль выполняет партнёр.

Выгрузка выбирает только общие ставки и разрешённые поля. Для SFTP нужны защищённое соединение, отдельный каталог и ограниченные права. Срок хранения и удаление файлов согласуются с банком и партнёром.

**Подготовка и проверки**

Форматы API и CSV согласуются в первый месяц. Справочник и API готовятся до подключения интерфейса кол-центра. SFTP готовится до проверки выгрузки.

Совместно проверяются изменение ставки, повторная отправка, неполный файл, просроченная версия и отказ канала.

Работы перечислены в [Tasks.md](Tasks.md), сроки показаны в [RoadMap.drawio](RoadMap.drawio).

### **Альтернативы**

1. Рассылать Excel по почте. Это временный вариант: при большом числе операторов сложно следить за актуальностью копий.
2. Дать кол-центрам доступ к Oracle. Это увеличивает нагрузку на АБС и риск доступа к закрытым данным.
3. Подключить оба кол-центра к Kafka. Для банка достаточно HTTPS, партнёр готов принимать файлы.
4. Создать отдельную систему управления справочниками. Для этого MVP достаточно АБС и копии ставок в сервисе депозитов.

**Недостатки, ограничения, риски**

- Получение файла зависит от расписания партнёра. Формат и допустимый возраст данных нужно согласовать.
- Ошибки отправки партнёру не должны мешать другим каналам. Отправка повторяется отдельно.
- Старая действующая версия может отличаться от новой. Оператор видит время обновления и прекращает использовать ставку после окончания её действия.
- Нужны доработка кол-центра подрядчиком и проверка загрузки данных у партнёра.
- План на шесть месяцев предварительный. Команды должны подтвердить сроки, инфраструктуру и готовность партнёра.
