### **Решение**

Схемы: [контекст](C4-context.drawio) и [контейнеры](C4-containers.drawio). Рядом находятся SVG для просмотра. На схеме контейнеров показано устройство интернет-банка и АБС.

**Сервис депозитов**

Создаём отдельный сервис на C#/ASP.NET Core. Он принимает заявки, показывает ставки и статусы, проверяет СМС-коды. Заявки и копия утверждённых ставок хранятся в отдельной базе MS SQL.

Сервис разрабатывает команда интернет-банка. В нём находятся HTTP API и обработчики фоновых задач. Основной интернет-банк продолжает работать на ASP.NET MVC.

Сервер интернет-банка обращается к сервису по HTTPS и передаёт подтверждённые данные вошедшего клиента. Сервис проверяет доступ к заявкам и персональным ставкам.

Сайт PHP/React обращается через свой сервер и получает только общие ставки. Заявка сайта сначала сохраняется в MS SQL. Затем фоновый обработчик передаёт её в кол-центр по HTTPS. При ошибке отправка повторяется с тем же номером заявки. Доработку API кол-центра нужно согласовать с подрядчиком.

**Изменения в АБС**

АБС хранит утверждённые ставки, их версии, сроки действия и состояние согласования. Excel используется для расчёта и загрузки ставок.

В Delphi добавляются формы работы со ставками и онлайн-заявками. Кредитный и депозитный отделы сохраняют разные права доступа. Между ними передаются результаты оценки и утверждённые ставки.

Для обмена добавляется сервис интеграции на Java Spring Boot. В банке есть специалисты Java. Учётные операции продолжают выполнять существующие процедуры PL/SQL.

Сервис интеграции получает заявки из Kafka и вызывает процедуры АБС. Ставки и статусы отправляет обратно через Kafka. Обработка идёт порциями с ограничением нагрузки на Oracle.

При отказе АБС сообщения ожидают обработки в очереди. Интернет-банк продолжает принимать заявки.

**Обмен сообщениями**

Через Kafka передаются сообщения об утверждении ставки, подтверждении заявки, согласовании условий и результате открытия. Каждое сообщение содержит идентификатор, версию и время. Для персонального предложения также указывается клиент.

Доступ к Kafka получают служебные учётные записи. Соединения шифруются. Старый интернет-банк к Kafka не подключается.

Заявка и запись о её отправке сохраняются одной транзакцией в MS SQL. АБС таким же способом сохраняет результат операции и запись для отправки в Oracle.

Фоновые обработчики отправляют сообщения и повторяют попытку при сбое. Получатели запоминают обработанные сообщения. Перед открытием счёта АБС проверяет номер заявки. Это защищает от повторного открытия по одной заявке.

Записи для отправки хранятся в служебных таблицах MS SQL и Oracle.

**СМС и подтверждение условий**

Сервис депозитов подключается к существующему СМС-шлюзу по согласованному интерфейсу.

Код связан с клиентом, заявкой, суммой, счётом и версией условий. Он используется один раз. Срок действия и число попыток нужно согласовать со специалистами по безопасности.

После согласования ставки и открытия депозита АБС передаёт события для отправки уведомлений. Если условия изменились, клиент подтверждает их заново. Полученное СМС само по себе не означает, что депозит открыт.

**Просмотр ставок и обработка заявки**

Сервис показывает ставки из своей базы MS SQL. Предложение с истёкшим сроком нельзя выбрать для новой заявки.

После сохранения заявки клиент получает её номер и статус. Система не ждёт завершения работы сотрудника.

Список счетов берётся через существующий механизм интернет-банка. Перед открытием АБС проверяет счёт и наличие средств.

Существующая прямая связь интернет-банка с Oracle остаётся для платежей и текущих счетов. Новый процесс её не использует.

**Размещение и восстановление**

Веб-часть и сервис депозитов запускаются в основном и резервном ЦОД. Балансировщик распределяет запросы между доступными экземплярами.

MS SQL хранит копии данных. Запись идёт через основной узел. При отказе выполняется управляемое переключение на резервный.

Для Kafka нужны копии сообщений и подтверждение записи. Размещение узлов, включая кворум, нужно определить отдельно с учётом отказа ЦОД.

Oracle использует существующую схему резервирования банка. Её мощность увеличивается за счёт ресурсов сервера. Добавление обработчиков не снимает ограничений базы.

Доступность 99,9% нужно подтвердить проверками отказов, переключения и нагрузки. Текущей инфраструктуры интернет-банка для этого недостаточно.

Предварительный ориентир для API: не менее 95% запросов выполняются за 500 мс или быстрее. До реализации нужно согласовать нагрузку, время восстановления, допустимую потерю данных и задержку обработки.

### **Альтернативы**

1. Доработать ядро интернет-банка и оставить прямую работу с Oracle. Это увеличивает нагрузку на АБС и зависимость от подрядчика.
2. Вызывать АБС с ожиданием ответа на каждое действие. Обмен проще, но отказ АБС остановит приём заявок, а просмотр ставок увеличит нагрузку.
3. Перевести весь интернет-банк на микросервисы. Для MVP за шесть месяцев это слишком большой объём работ.

**Недостатки, ограничения, риски**

- Ставки и статусы обновляются с задержкой. Нужны проверка версий и контроль задержек.
- Kafka и новый сервис требуют сопровождения. Поддержку нужно обучить, восстановление обмена — проверить.
- Работа сотрудника остаётся ограничением MVP. Мгновенное открытие не обещается.
- Нужно согласовать подключения к СМС-шлюзу и кол-центру, способ электронного согласия и состав документов. Новый клиент проходит проверку документов до открытия счёта.
- Работа между ЦОД зависит от сети, копирования данных и размещения узлов Kafka. Доступность подтверждается испытаниями.
